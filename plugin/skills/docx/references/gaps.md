# Known gaps of the pinned build (docx)

Each gap is a strict expected failure in `tests/` (key in brackets): the day a new pin closes it, the suite
says so, and this page is updated. "Fallback" means: do that step only with the default `docx` skill
(python-docx, lxml or LibreOffice), and keep rdocx for the rest and for the verification.

Before reaching for lxml, try the raw XML of the element (`paragraph.xml` / `replace_xml`, also on runs,
tables, cells and `doc.section(i)`; `doc.part_xml(name)` reads any XML part but the relationships and
`[Content_Types].xml`: `references/python-api.md`, "Raw XML").

| Gap | What happens | Workaround / fallback |
|---|---|---|
| Edits of a large document [docx-edit-cost-grows-with-body] | 145 of the 252 calls `tests/test_docx_scaling.py` times cost a time that grows with the body's XML, whatever the element edited: adding, inserting, moving or removing content (paragraphs, headings, tables, pictures, charts, list items, notes, comments, sections), text (`p.text`, `run.text`, `cell.text`, replacements), `replace_xml`, table structure and cell edits, content controls, hyperlinks, revisions, headers, footers, watermarks, fonts, numbering, and reading `p.xml`. In a body of 1000 paragraphs as Google Docs writes them (2.4 MB of XML), `insert_paragraph` and `remove_content` take about 0.5 s a call, `p.xml` 0.15 s. Constant: run, font and paragraph formatting (`run.bold`, `font.*`, `paragraph_format.*`, `p.style`, `p.alignment`), page setup (`doc.section(i)` sizes and margins, `update_section`), styles, document defaults, bookmarks, document properties | Edit the structure in few calls: one `remove_content_range(start, end)` for a run of blocks (70 blocks of that body: 1.8 s, against 35 s one by one), and the new content built in a document aside, then one `insert_document` (70 paragraphs: 3 s against 40 s). Build that document in a copy of the target emptied by one `remove_content_range` (`rdocx.Document.from_bytes(doc.to_bytes())`): a new `rdocx.Document()` does not go in (below). To read the XML of many paragraphs, parse `doc.part_xml("word/document.xml")` once with `xml.etree.ElementTree`: 0.5 s for that body, against 0.15 s a paragraph |
| Inserting a document whose pictures the target already holds [docx-insert-document-reused-picture-swapped] | With the default policy, `insert_document` reuses the target's picture parts that hold the bytes of the inserted pictures, but pairs them in the wrong order: an inserted drawing, its size and description its own, shows another picture of the document. Met when a tool regenerates figures into a document that already holds them | `doc.insert_document(other, at=bi, policy=rdocx.FragmentConflictPolicy.reuse_equivalent().with_related_part_reuse(False))`: each inserted picture keeps its own bytes. Build `other` from a new document, not from a copy of the target's package: with image relationships its body no longer used, two inserted drawings swapped their relationship ids even with reuse off. Check after inserting: each `p.bytes` of `doc.pictures()` against the bytes inserted |
| Inserting a document whose styles part defines an id twice [docx-insert-document-duplicate-style-ids] | When `word/styles.xml` defines a `w:styleId` twice with different values (Google Docs writes such parts) and the inserted document carries the same part, `insert_document` adds a `<id>Merge1` copy of each such style (`Heading1Merge1`) and gives it to the inserted paragraphs, again at each run of the tool | Before inserting, keep only the first definition of each style id in the inserted document: rewrite `word/styles.xml` in `other.to_bytes()` with `zipfile` and open the result with `rdocx.Document.from_bytes`; then no style is added. `with_style_reuse(True)` changes nothing. Check after inserting: no `Merge` in `[s.style_id for s in doc.styles]` |
| A new document inserted into one from Word [docx-insert-document-new-document-refused] | `insert_document(other, ...)` and `import_fragment` with a new `rdocx.Document()` as the source raise `RdocxError` ("invalid style graph: style type 'paragraph' has more than one default") when the target's Normal style differs from rdocx's own, which is the case of every document Word, Google Docs or python-docx writes, whatever the `policy` | Build the content to insert in a copy of the target (`rdocx.Document.from_bytes(doc.to_bytes())`) whose body one `remove_content_range(0, end)` emptied, keeping its last paragraph, or in a document opened from the target's template; with pictures, check them after inserting (above) |
| A comment across two table cells [docx-comments-range-across-cells] | `doc.comments` and `rdocx comment list` raise (`RdocxError`: "cannot be projected faithfully") as soon as one comment's range starts in a cell and ends in the next one, as Google Docs writes a comment made on a selection across cells: one such comment blocks the listing of all | `remove_comment(id)` works on such a document. `doc.part_xml("word/comments.xml")` gives each comment's id, author and text, not its anchor. Fallback for the listing: python-docx's `Document.comments` (id, author, text) |
| Relationships and content types [docx-part-xml-without-relationships] | `part_names()` lists neither the `.rels` parts nor `[Content_Types].xml`, and `part_xml` refuses them (`RdocxError`): no API resolves a relationship id (a link's, a picture's, a header's) to its target or gives a part's content type | Read them from the saved package, read-only: `doc.to_bytes()` unzipped with `zipfile` (`word/_rels/document.xml.rels`, `[Content_Types].xml`). A picture's part and a link's target have their own API: `Picture.media_part_name`, `Hyperlink.url` |
| A multiple as the default line spacing [docx-default-line-spacing-multiple] | `doc.set_default_paragraph_format(line_spacing=1.15)` raises `TypeError`: it takes a length, which writes an exact pitch (`w:lineRule="exact"`), and no multiple (`auto`), the rule of Word's own default (1.08 lines). Reading one works | `doc.set_style("Normal", line_spacing=1.15)`: the paragraphs that follow Normal, and the styles based on it, take it |

A step that rdocx blocks, or gets wrong, and that this page does not list is a new gap: report it as
`SKILL.md` describes (Reporting a bug or a missing feature).
